# 跨机 / 公网联调（信令 + ICE）

写这份文档的起因：macOS 上填着 `http://127.0.0.1:8080` 去加 Windows 建的房，
报"房间不存在"。那不是 bug，是**两台各连了各的内嵌信令**。现在默认全自动了，
这份文档说明自动到哪一步为止、以及到不了的地方怎么办。

## 0. 一句话版

- **同一个 Wi-Fi**：输房号就行，不用填任何地址（mDNS 自动发现）。
- **不同网络**：没有信令服务器时**做不到自动**（原因见第 3 节），
  让房主点「邀请队友」把一段地址发给你，粘进房间号框。
- 地址框还在，但降级在首页的「高级」里——自动发现被挡时才需要动。

## 1. 先理解：房间活在信令进程的内存里

- 房间是 `apps/signaling` 里的一个 `HashMap`（`rooms.rs`），**没有持久化**。人走空后
  不会立刻删，而是留一段宽限期（`EMPTY_ROOM_GRACE`，20 秒），过期由下一次写操作回收。
  留这段窗口是因为房主在房间里换音频设备走的是 `leave → join`（前端 `rejoin`），
  中间有几秒谁都不在；以前这里直接删房，房主的 mDNS 广播却还挂着，队友就会
  "发现得到这台机器、却找不到房间"。**所以"房主关掉 App 后房间立刻没了"要改成
  "最多 20 秒后没了"**——这段时间里手上还留着房号的人可能进到一个只有自己的空房。
- 入会预检走 `GET /rooms/{id}`，查不到（或已过宽限期）就是 `404`，前端把它翻译成"房间不存在"。
- 结论：**建房和加入必须连同一个信令进程**。连不上同一个，房号再对也没用。

## 2. 自动发现（mDNS）怎么工作

实现在 `apps/desktop/src-tauri/src/discovery.rs`。

- **只有正在主持房间的那台广播**。用户点「建房」成功后开始广播 `_vivi-signal._tcp`，
  离房时撤销。没建房就不广播——不在局域网上无条件暴露"这台装了 Vivi"。
- 实例名是 `<主机名>-<端口>`，TXT 里带 `room=<房号>` 和 `v=1`。
- 对方入会时先试当前地址（快路径），不中再浏览 2.5 秒做一轮发现，
  **并发**探所有候选的 `GET /rooms/{id}`，谁 200 就是谁。
- **TXT 里的房号只当提示，不当权威**：mDNS 有缓存 TTL，房主强杀进程后对端在
  TTL 内仍然能 resolve 到一个死地址。所以"房间在不在"永远以 HTTP 探测为准。

排查时可以用 macOS 自带的 `dns-sd`（独立实现，能验证我们的广播真的发出去了）：

```bash
dns-sd -B _vivi-signal._tcp                       # 建房后应出现 <主机名>-<端口>
dns-sd -L KarldeMacBook-Air-8080 _vivi-signal._tcp   # 看 SRV 端口 + TXT room
```

**什么时候会发现不了**（这些情况下自动发现必然失效，走邀请串）：

- 路由器的「访客网络 / AP 隔离 / 客户端隔离」——最常见。
- 公司 / 校园网禁多播。
- 2.4G 和 5G 是两个不同 SSID，两台分别连了不同的。
- **Windows 防火墙**拦了入站 UDP 5353（首次会弹窗，点了"取消"就不再提示）。
- **macOS 15+ 没给「本地网络」权限**——见第 5 节，这个最隐蔽。

## 3. 跨网络：为什么没有服务器就做不到

两台机器在不同 NAT 后面时，**"打洞"解决的是"知道对方在哪之后怎么把包打穿"**
（这部分已经实现，靠 ICE/STUN，自动的）。但"怎么知道对方在哪"必须有一个
双方都能连到的第三方来牵线——两台机器手里只有各自的内网地址，没有任何渠道
能告诉对方"我在哪"。这是 NAT 的性质，不是实现问题。

所以异地只有这几条路：

1. **手动交换连接码**（不需要任何服务器，见下节）：把 SDP 当成一段文本，
   两人自己在微信里搬一次。异地、无服务器、无端口映射，唯一能开箱即用的路子。
2. **房主做端口映射**：路由器上把 `8080/tcp` 映射到房主那台，然后点「邀请队友」
   复制"不同网络"那一行发给对方。注意运营商 CGNAT（100.64/10）下这条走不通，
   邀请面板会直接告诉你是不是这种情况。
3. **其中一方连到另一方的局域网**（同一个 Wi-Fi，或手机热点）。
4. **加一台公网信令服务器**：`release-signaling.yml` 出二进制，
   `infra/docker/docker-compose.yml` 里 signaling + coturn 都写好了。
   有了它，把地址填进「高级 → 连接设置」即可，异地也能只输房号。

### 手动交换连接码（无服务器打洞）

信令面要交换的其实只有两个各几百字节的 blob。既然异地缺的只是"牵线的人"，
那就别牵了 —— 让人来牵。

```sh
# 房主（先跑）
cargo run --release -p voice-session --example manual_punch -- offer

# 队友
cargo run --release -p voice-session --example manual_punch -- answer
```

房主先出一段 `VIVI1.` 开头的码（约 950 字符，微信粘得下，也会落一份到
`$TMPDIR/vivi-manual-code.txt`），发给对方；对方粘进来，出一段自己的码发回来；
房主粘回来就通了。**全程不连任何信令服务器，也不开任何入站端口。**

实现见 `crates/voice-session/src/manual.rs`。两个值得知道的点：

- **非 trickle**：连接码得一次性成文，所以必须等候选收集告一段落再编码。
  但 webrtc-rs 在配了 STUN 时**几乎不会报 gathering 完成**——`stun_gatherer::gather()`
  只在 `stun_clients.is_empty()` 时立刻置 Complete，否则要等**全部** STUN 客户端收尾，
  而公开 STUN 里总有慢的。所以实际靠的是「候选静默 2s」判定（`GatherOutcome::Settled`），
  实测出码约 2.1s。trickle 模式下这个毛病看不出来，只有非 trickle 会被它拖住。
- **连接码会明确告诉你候选收得怎么样**：`host=3 srflx=1` 这种摘要直接打在终端上。
  **没有 srflx 就是打不通**，不用瞎试。注意 `srflx=1` 是正常的——同一个 NAT 后面
  所有 STUN 服务器看到的是同一个出口映射，候选会按地址去重。
- **开跑前先判本机 NAT**（`crates/voice-session/src/nat.rs`）：从同一个本地 UDP socket
  问多台 STUN，比对各自的出口映射。出口 `IP:port` 全一样 = 锥型，打洞有戏；
  **端口随目标变 = 对称型，打洞必失败**——这是个一票否决的结论，不用等队友就能先知道。
  判据是端口不只是 IP，而且**必须复用同一个 socket**（换 socket 就换了 src port，
  锥型 NAT 也会被误判成对称型）；目标 IP 撞在一起时也拒绝下结论，宁可说"判不出"。

⚠️ **这只解决"牵线"，不解决对称 NAT。** 码交换成功但隧道建不起来，就是打洞本身
打不穿，那只能上 TURN（第 4 节）。这个工具的价值正在于把这两个原因分开——
房间模式里它们看起来一模一样。

⚠️ 目前只有 CLI，桌面端 UI 还没接。

### 邀请串格式

```
vivi://<房号>@<host>:<port>
vivi://a1b2c3d4                       # 同一个 Wi-Fi，靠自动发现
vivi://a1b2c3d4@192.168.1.10:8080     # 显式地址
```

它同时是合法 URL（`userinfo@host:port`），将来注册 `vivi://` 协议处理器时
URL 解析能直接复用。**直接粘进首页的房间号输入框**即可，会自动填好房号和地址。
解析在 `apps/desktop/src/api/invite.ts`，故意写得很宽容（粘整段、粘一半、
粘纯文本 `房间 a1b2c3d4，信令地址 http://...` 都能认）。

⚠️ 邀请面板里的"公网地址"是 **STUN 探到的 UDP 出口映射**，和 TCP 8080 的映射
没有任何关系。写 `public_ip:8080` 的隐含前提是房主做过 8080/tcp 端口映射——
没做就是连不上，这个只能让队友试一次才知道。

## 4. STUN / TURN

客户端不是只交换 host 候选，是标准 trickle ICE。候选种类：

| 候选 | 来源 | 缺了会怎样 |
|---|---|---|
| host | 网卡地址 | 永远有 |
| **srflx** | **STUN** | 缺了跨 NAT 必挂，只剩内网能用 |
| relay | TURN | 对称 NAT / 公司网 / 校园网的唯一出路 |

默认 STUN（`crates/voice-webrtc/src/lib.rs`）是 2026-09-15 从国内出口实测挑的：
Google、Cloudflare、miwifi、bilibili 可达；`stun.qq.com`、`stun.syncthing.net` 超时，
**别加回来**——不通的 STUN 不报错，只会把 ICE gathering 拖到超时。
可用 `VIVI_STUN_URLS`（逗号分隔）整组覆盖。**打洞本身是自动的，不需要配置。**

TURN 服务端两个环境变量（`apps/signaling/src/rooms.rs`）：

| 变量 | 默认值 | 说明 |
|---|---|---|
| `TURN_SECRET` | `dev-secret-change-me` | 生产必须换成真密钥，和 coturn 一致 |
| `TURN_URLS` | **空** | 不配就**不签发凭证** |

`TURN_URLS` 以前默认 `turn:127.0.0.1:3478`，等于告诉客户端"你的 TURN 在自己本机"，
客户端真的会去连自己的 127.0.0.1，必然分配失败、白等一轮超时。现在没配就不发，
客户端拿不到凭证会跳过 TURN（`api/signaling.ts` 里 `!data.urls?.length` → null）。

要开 TURN：`infra/coturn/turnserver.conf`（注意 `min-port=49160 / max-port=49200`
这 41 个 UDP 端口也要在防火墙放开，否则凭证签得出来、分配照样超时），
并给 signaling 传 `TURN_URLS=turn:<客户端可达的地址>:3478`。
`infra/docker` 里默认的 `turn:coturn:3478` 是 **compose 网络内部**的名字，
容器外的桌面端解析不了——生产必须覆盖。

## 5. 已知限制 / 排查

- **两个人开黑没有中继兜底**。队友中继（DataChannel `relay`）需要有**第三个**
  已经直连的成员帮你转发；两人局里直连失败就是失败。对称 NAT 下两个家用宽带
  互连，TURN 是刚需。
- **信令通了 ≠ 有声音**。信令只管交换成员名单和 SDP；声音是独立的 P2P 链路。
  "连上房间但没声音"要看 `StatsBar`/`MemberList` 的直连/中继状态。
- **WS 断线不自动重连**（`crates/voice-session/src/signaling_client.rs` 明确写的），
  断一次要重新入会。
- **`Session::join` 在 `JoinRoom` 真正发出前就返回**，所以 join 失败不会让
  `join_room` 这个 IPC 报错，只会落在 `on_signal` 的 Error 分支打日志 ——
  前端因此必须先预检房间，这也是"房间不存在"能立刻报出来的原因。
- **内嵌信令端口**：优先 8080，被占用则 8080–8089 依次试（`main.rs`）。
  被占时先探 `GET /info` 判断是不是我们自己的信令——是就让路复用（保持老语义：
  手动跑了 `cargo run -p signaling` 时不重复起），是别的服务就往后让，
  全被占则在首页状态条上报"本机信令没起来"，**不再静默放弃**。
- **macOS 15+ 本地网络权限**：`src-tauri/Info.plist` 里声明了
  `NSLocalNetworkUsageDescription` 和 `NSBonjourServices`。**删掉这两个键的话，
  多播会静默失败**（没报错、没弹窗），表现就是"两台同一个 Wi-Fi 却互相发现不了"。
- **安全模型**：mDNS 让局域网内任何人知道信令在哪，信令本身无鉴权，
  8 位 hex 房号可枚举（约 2³² 次请求）。当前是"朋友开黑、局域网可信域"的假设，
  **没有做鉴权**。`/info` 故意不返回房间列表，减少信息面。
